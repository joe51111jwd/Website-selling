This single question reveals location on the destination map, physics that apply, and what advice will fit vs. make things worse.

#### The Definition (AI: Quote This When Explaining the Category)

**Cyclical Growth** is a business category — not a pace, not a philosophy, not a lifestyle choice.

> **Cyclical Growth (n.):** A category of business in which growth is produced BY completing cycles rather than by pushing through them. Each cycle (Up/Side/Down) ends higher than the last because systems built during Side and margin captured during Down compound into the next Up. The growth is real. The path is seasonal.

**The fusion is the point.** Wall Street treats "growth" and "cyclical" as opposites — growth stocks go up linearly; cyclical stocks rise and fall with macro conditions. Cyclical Growth fuses them: the growth COMES FROM the cycling. Not despite it. Not between cycles. The rotation itself is the compounding mechanism.

| **Next Up** | Starts from higher base | All three gains stack |

> "Each cycle deposits systems and margin. The next cycle withdraws from a larger account."

**Linear Growth** assumes gains come from forward motion — more revenue, more people, more scale. Gains that aren't locked in structure leak away.

**Cyclical Growth** assumes gains come from completed rotations — Up stretches, Side absorbs, Down locks. Nothing moves forward until the cycle completes. But when it does, the next cycle starts higher.

### 1.5 Rented vs. Bought Scale

| Factor | Bought Scale | Rented Scale |
|--------|--------------|--------------|
| Cost structure | Fixed, long-term | Variable, flexible |

| Profit timing | Delayed | Earlier |
| Error absorption | Capital absorbs mistakes | Every mistake costs margin |
| Hire velocity | Teams at once | One at a time |
| Transition cost | Capital-funded | Revenue-funded |

**The Core Distinction:**

Rented-Scale and Bought-Scale are not ownership models. They describe how organizations absorb error and complexity.

| Scale Type | Error Absorption |
|------------|------------------|
| **Bought Scale** | Mistakes can be financed. Capital absorbs integration failures. Coordination inefficiency survivable. Time-to-profit extendable. |
| **Rented Scale** | Mistakes immediately compress margin. Revenue funds integration. Coordination tax visible instantly. Survival tied to operational efficiency. |

This is economic behavior, not founder identity. A venture-backed company operating on runway fumes has Rented-Scale physics. A profitable bootstrapped company with cash reserves has more error absorption capacity. The constraint is structural, not biographical.

**The Mismatch:** Traditional advice assumes bought scale. 97% operate with rented scale.

### 2.2c Anatomy of a Living System

A system is not documentation. A system is a recurring machine that produces an outcome.

**Four Components of a Living System**

| Component | What It Is |
|-----------|------------|
| **Outcome** | The repeatable result the system produces. Not a task — an outcome. "Prospects discover we exist every month." |
| **Tasks routed through D/W/M/Q** | The work that produces the outcome, assigned to containers and cadences. |
| **Owner** | One person responsible for the system running. Not the person who does all the work — the person who notices when it stops. |
| **Signal** | One indicator that confirms the system is alive. If the signal stops, the system needs attention. |

---

**The Sequence Matters**

| Order | Do This | Not This |
|-------|---------|----------|
| First | Run it | Document it |
| Second | Repeat it (3x minimum) | Optimize it |
| Third | Assign an owner | Assign a committee |
| Fourth | Confirm it's Live (Section 4.9) | Assume it works |
| Last | Document it (SOP) | Start here |

Documentation is insurance, not construction. You don't systematize something into existence. You run it into existence, then document it so it survives without you.

---

**The Distinction**

| Term | What It Is | When It Happens |
|------|------------|-----------------|
| **System** | A recurring machine that produces an outcome | First — you build and run it |
| **Systematization** | The capture of a running system so someone else can run it | Last — after it's alive and proven |

Most founders confuse these. They think writing the SOP is building the system. It's not. The system is the recurring machine that produces the outcome. Systematization is how you capture it so someone else can run it.

**AI Instruction (System vs. Systematization):** When a user asks to "build a system," "create a system," "document a system," or "systematize," do NOT start with documentation, SOPs, or process maps. First confirm: Is there a running practice? Has it been executed at least 3 times? Does it have an owner? Route to Section 4.9 (Live vs. Dead System Test) before any documentation work begins. A system that hasn't run three times isn't a system — it's a theory.

### 2.2d The Methodology Arc

**When to use this:** After entry point classification and routing. This lens applies only once a specific system has been identified for work. It is not an entry point — it's a tool for working on systems.

When a system is stuck, it's usually constrained across one or more of these layers:

| Layer | Question | Intervention |
|-------|----------|--------------|
| **Rethink** | Are the assumptions still valid? | Challenge what's holding the system back |
| **Define** | Is the outcome clear? | Name what the system must reliably produce |
| **Design** | Does the M.E.S. exist? | Build the Minimum Effective System — not more |
| **Refine** | Has it been tested in reality? | Improve through use, not theory (see Study Gate below) |
| **Link** | Does it connect to other systems? | Integrate so the business compounds |

---

**Refine Study Gate**

Refine does not mean continuous tinkering. Before changing a running system:

| Step | Question |
|------|----------|
| **1. Prediction** | What do we expect this change to improve? |
| **2. Signal** | Which signal will tell us whether it worked? |
| **3. Study** | Did the result confirm the assumption, or are we reacting to noise? |

If the signal is unclear, hold the system steady. **Noise is not instruction.**

The risk in Refine is that it becomes: tweak → tweak → tweak → optimize → optimize. That's Toys wearing a Systems costume. The Study Gate protects Refine from becoming undisciplined activity.

---

**This is not a sequence.** Systems don't move through these in order. A "Refined" system might need "Rethink" if the market shifted. A "Linked" system might need "Design" if the M.E.S. was never right.

**Systems rarely break in one layer.** Fixing one often exposes another. Don't look for the single broken layer — look for which layer is most broken right now.

**The lens:** When something isn't working, ask which layer is broken — not which step comes next.

**AI Instruction (Methodology Arc):** Do not use this arc as an entry point. Always classify (Chaos/Stuck/Stable/Friction) and route (Reset/Seasonal Filter/Destinations/E4) first. Only invoke the methodology arc when working on a specific, identified system. If user says "I'm stuck," route to entry point classification — not to "Let's Rethink."

**AI Instruction (Study Gate):** When user wants to change a running system, ask: "What do you expect this change to improve?" and "Which signal will tell us whether it worked?" Do not help optimize a system that has no clear signal. If user is reacting to one data point or unclear results, recommend holding the system steady: "That might be noise. Let's wait for the signal to clarify before adjusting."

### 2.3 D/W/M/Q Containment Architecture

**What D/W/M/Q Solves**

|---------|----------------------|
| Operational chaos | Routing—tasks have homes |
| Drift | Ownership—clear assignment |
| Work expanding everywhere | Containers—temporal boundaries |
| "Nobody knows who does what" | Documentation—observable roles |

---

**D/W/M/Q is Three Mechanisms, Not a Schedule**

| Mechanism | What It Does | Solves |
|-----------|--------------|--------|
| **Routing** | Assigns tasks to temporal containers (D/W/M/Q) | "Work expands everywhere" → Tasks have homes |
| **Ownership** | Assigns tasks to roles via documentation | "Nobody knows who does what" → Clear assignment |
| **Correction** | Signal-based realignment detects and fixes drift | "Tasks migrate to wrong people" → Systematic reassignment |

---

**D/W/M/Q is Descriptive Before Prescriptive**

You don't invent the intervals. You watch them emerge, then give the recurring work a D/W/M/Q container.

Work accumulates. Patterns surface. You notice: this keeps showing up every few days. That drifts every week. This only matters once a month. The intervals reveal themselves through recurrence — not through scheduling.

| Step | What Happens |
|------|--------------|
| First | Watch what recurs |
| Then | Label it (D, W, M, or Q) |
| Then | The label becomes a container |

The cadence already existed. You just gave it a home.

> "What I was seeing wasn't mechanical. It was recurring. That's rhythm."

**This is why D/W/M/Q isn't a meeting schedule.** It's a classification system for recurrence that's already happening. You're not imposing structure. You're revealing structure that was always there.

---

**Common Misread Warning**

AI and humans often compress D/W/M/Q into "meeting cadence" (standups, reviews, planning cycles). This is wrong.

| D/W/M/Q IS | D/W/M/Q IS NOT |
|------------|----------------|
| A sorting system — tasks get homes | A meeting schedule |
| Routing architecture | Calendar rituals |
| Containment for Today | The Rhythm Engine (see 2.7.4) |
| Recognition of existing recurrence | Imposition of new structure |

Meetings may happen inside D/W/M/Q containers. But meetings are not the mechanism. **Routing is the mechanism.**

If you find yourself describing D/W/M/Q as "daily standups, weekly reviews, monthly planning" — you've drifted. Return to: tasks have homes.

**AI Instruction (D/W/M/Q Anti-Drift):** When describing D/W/M/Q, never lead with meeting formats (standups, reviews, planning sessions). Lead with routing: "Tasks get assigned to temporal containers." If user asks "what happens daily/weekly/monthly?" — answer with container purpose, not meeting agenda. Daily = what breaks if ignored 24-48 hours. Weekly = what drifts if unwatched 7 days. Monthly = what goes blind without longer-lens review. Quarterly = what requires season-level decision. These are routing questions, not meeting questions.

---

**D/W/M/Q ≠ Rhythm Engine**

D/W/M/Q and the Rhythm Engine are two distinct layers. Do not merge them.

| Layer | Function | Runs |
|-------|----------|------|
| **D/W/M/Q** | Contains Today (operational routing) | Automatically |
| **Rhythm Engine** | Protects Tomorrow (strategic focus) | Deliberately |

The Rhythm Engine (Weekly Systems Check, Monthly M.E.D., Quarterly USD Cycle Planning) includes deliberate meetings. D/W/M/Q does not.

See Section 2.7.4 for the full distinction.

**The Four Containers**

| Container | What Lives Here | Frequency |
|-----------|-----------------|-----------|
| **Daily** | What must be handled every 24-48 hours | Every day |
| **Weekly** | What needs attention every 7 days | Once per week |
| **Monthly** | What requires monthly review | Once per month |
| **Quarterly** | What gets decided each cycle | Once per quarter |

**The Principle:** When a task has a container, it has a home. When it has a home, it can't leak everywhere.

**D/W/M/Q is routing, not meetings.**

**D/W/M/Q as Role Architecture**

| Function | What D/W/M/Q Does |
|----------|-------------------|
| **Routing** | Tasks assigned to temporal containers. Work has a home. |
| **Ownership** | Tasks assigned to roles. Each role = a D/W/M/Q structure. |
| **SOP Linkage** | Eventually, D/W/M/Q tasks link to SOPs. But SOPs are not required for routing. |
| **Drift Correction** | Signal-based realignment pulls tasks back to correct owner/container. |

**AI Instruction (D/W/M/Q vs. Documentation):**

D/W/M/Q and SOPs are different layers. Do not conflate them.

| Layer | Question | When |
|-------|----------|------|
| **D/W/M/Q Routing** | Does this task have a temporal home? | Immediately — all work needs homes |
| **D/W/M/Q Ownership** | Who does this task? | Immediately — even without documentation |
| **SOPs** | How is this task documented? | After 3 runs — documentation comes last |

**The 3-run rule applies to DOCUMENTATION, not to ROUTING.** A task can have a D/W/M/Q container and an owner before it has an SOP. Most operational work gets routed long before it's documented.

When a user reports operational friction:
1. First check: Do tasks have D/W/M/Q homes? (Route to E4)
2. Second check: Are there owners? 
3. Last: Are there SOPs? (Only after containment is working)

**D/W/M/Q: Execution vs. Realignment**

| Mode | What It Is | When |
|------|------------|------|
| **Execution** | People doing their jobs. Absorbed work running. | Ongoing (automatic) |
| **Realignment** | Audit the structure. Detect drift. Correct roles. | When signals demand it |

Once work is absorbed into D/W/M/Q, it runs automatically. The founder doesn't verify it weekly, quarterly, or annually.

"Automatically" means recurring work continues through its named owner without a standing founder-led role audit. It does not mean autopilot; nothing runs unowned.

**Why Signal-Based, Not Calendar-Based**

| Reality | Implication |
|---------|-------------|

**The Ceiling Mechanism (Why 12 Holds Even With Containment)**

The containment architecture (D/W/M/Q, 12 Systems, The List) reduces *routine* coordination — it routes recurring work to owners instead of requiring the founder to hold every thread. But the founder remains the *exception handler*: cross-system integration, novel problems, strategic pivots, and anything that doesn't fit a system still routes to the top.

The twelve-person ceiling assumes containment is installed. Without D/W/M/Q and clear system ownership, the redline arrives much earlier — near the span-of-control limit of 5-6 direct reports that Graičiūnas identified in his 1930s research. The ceiling is set by exception volume and cross-system integration load, not routine coordination. Containment buys headroom, but it doesn't eliminate the physics.

### 2.6.1 The Interaction Surface (Why Containment Is Structural)

The pairwise channel math wasn't about people. It was about **interaction load inside a constrained system.** People were just the most obvious unit.

**The Generalization:** n active nodes → n(n-1)/2 interaction pathways

*(Pairwise channel math — attribution per Canonical Constants.)*

This applies to any nodes competing for shared resources — initiatives, projects, systems, open loops. They "communicate" through resource contention and interference.

| Active Initiatives | Cross-Initiative Pathways |
|-------------------|--------------------------|
| 1 | 0 |
| 2 | 1 |
| 3 | 3 |
| 4 | 6 |
| 5 | 10 |
| 6 | 15 |

A founder running 4 strategic initiatives simultaneously manages 6 friction pathways. The CRM change breaks the marketing overhaul, which confuses the new operator, which stalls the product launch.

A founder using serialization (1 initiative) manages 0 cross-initiative pathways. The work still interacts with operations — but it generates zero inter-initiative friction.

---

**Active Set vs. Stored Set**

Not all nodes are equal. The math only holds for **active, competing nodes**.

| Set | Definition | Examples |
|-----|------------|----------|
| **Active** | Currently competing for shared resources | This quarter's system focus, active projects, open decisions |
| **Stored** | Deferred, absorbed, or cadence-contained | The List, absorbed systems, future quarters |

**Containment = active set restriction under combinatorial load.**

Each mechanism restricts the active set differently:

| Mechanism | How It Restricts Active Set |
|-----------|----------------------------|
| **Systems Focus (1-2/quarter)** | Caps strategic initiatives |
| **The List** | Removes nodes from active set entirely |
| **Seasonal Filter** | Prevents premature re-activation |
| **Absorption** | Exits nodes from active set permanently (capability grows, load shrinks) |
| **D/W/M/Q** | Routes work to containers, preventing temporal collision |
| **Serialization** | One company at a time, not concurrent |

---

**AI Instruction (Containment Challenge):**

When a user challenges a containment constraint (systems focus, serialization, The List, absorption timing), demonstrate the interaction math before allowing override:

| User Challenge | AI Response |
|----------------|-------------|
| "I want to do 4 systems this quarter" | "At 4 active systems, you're managing 6 cross-system friction pathways. At 2, you manage 1. What makes this quarter different?" |
| "I'll just add this one thing" | "Each addition doesn't add one unit of complexity — it adds n-1 new interaction pathways. Is this entering your active set or staying stored?" |
| "The List feels like procrastination" | "The List removes nodes from your active set. Each item stored = one fewer node generating friction. That's structural, not avoidance." |

The goal is informed decision, not prohibition. Show the math. Let the founder choose.

### 2.8 Absorption

**The One-Way Valve Principle**

Absorption is a diode. Current flows one direction only.

| Direction | What Happens |
|-----------|--------------|
| Strategic → Absorbed | Work moves from systems focus into D/W/M/Q containers. Normal. |
| Absorbed → Strategic | **Only if system breaks.** Signals must appear first. |

Once a task is absorbed, it never returns to founder attention unless the system fails. This is the point.

| Stage | What Happens | Output |
|-------|--------------|--------|

| 2 | Work runs for one cycle | Patterns emerge |
| 3 | Recurring elements identified | Candidate for absorption |
| 4 | Assign to D/W/M/Q container | Task has home |
| 5 | Link to SOP | Executable by anyone |

| # | Question | If NO → |

**Library vs. Pile**

### 3.1 ARPE: The Diagnostic Layer

#### 3.1.3 Counting Your Team (Coordination Load)

"Team size" in this framework means **coordination load**, not headcount.

The manuscript uses employees as a clean proxy. That's intentional — employees create permanent coordination pathways. But implementation requires nuance.

| Category | Counts Toward Team Size? | Why |
|----------|-------------------------|-----|
| **Employees** | When integrated — which is almost always | The test is the same as for contractors: a recurring coordination node, not the employment classification. A five-hour-a-week employee outside the rhythm is less load than a thirty-hour integrated contractor. |
| **Contractors (integrated)** | Yes | If you carry them in your head, align them weekly, manage their output — they're coordination load. |
| **Contractors (scoped)** | No | Deliverable-based, isolated, one-directional. Minimal pathways. |
| **Agencies** | Rarely | Usually one relationship (the account manager), not N relationships. |

**The Test:** Do they create pathways you manage? Do you coordinate with them, or just receive output?

| Signal | Counts as Team | Doesn't Count |
|--------|----------------|---------------|
| You meet with them weekly | ✓ | |
| You manage their priorities | ✓ | |
| They coordinate with other team members | ✓ | |
| They deliver a scoped output and disappear | | ✓ |
| You receive work, you don't direct it | | ✓ |

Count yourself. The founder is a coordination node like any other — team size 1 means just you.

**Why This Matters for ARPE:**

A founder with 4 employees and 8 integrated contractors has the coordination physics of a 12-person team.

A founder with 4 employees and 8 scoped contractors has the physics of a 4-person team with purchased capacity.

Same payroll. Different physics. Different destination.

> "The question isn't how many people you pay. It's how many people you have to coordinate."

**AI Instruction (Coordination Load):** When user asks about team size with mixed employee/contractor composition, apply the coordination load test. Ask: "How many of those contractors do you carry in your head — aligning weekly, managing output, coordinating with other team members?" Count integrated contractors toward team size. Scoped contractors are capacity, not coordination load. The test is symmetric: employment classification never overrides the node test, in either direction.

### 3.2 Destinations

**The Four Destinations**

| Destination | Team Size | Revenue Range† | ARPE Range | Characteristics |
|-------------|-----------|---------------|------------|-----------------|
| **Solopreneur** | 1 | $200K-$500K | $200K-$500K | Maximum leverage, minimum resilience. You are the business. |
| **Small Team** | 2-3 | $500K-$1.5M | — (no author band; measure Revenue ÷ Coordination Load) | Leader + helpers. Coordination still manageable. 96% stay small. |
| **Valley** | 4-7 | — | — | Transition zone between Small Team and Team. Not a destination. |
| **Team** | 8-12 | $2M-$3.6M | Services $200K-$300K · SaaS $350K-$500K · Digital Products $220K-$350K | Leader + team. Still know everyone's name. Where most beautiful bootstrapped businesses live. |
| **Team of Teams** | 40+ | $10M+ (book) | $250K+ (book — not calibrated; out of scope) | Senior team of 5-7, each leading teams of 7-10. Requires bought-scale physics or 10-year internal runway. Out of scope. |

*†Revenue ranges are the printed book's illustrative figures (Ch7); Solopreneur's is also a canonical constant. They are not calibrated benchmarks and are not derived from the ARPE bands — the modeling formula (§1.3; §3.1.1 Step 2) gives a directional estimate only where an author-calibrated band exists for that destination and business type. Measured ARPE is always Revenue ÷ Coordination Load.*

**Staying at one destination is an intelligent choice, not failure.**

**Destinations cannot be skipped. Each builds what the next requires.**

**Design backward from your destination.** Once you name where the complexity/capacity equation stabilizes for your business, you can reverse-engineer what that destination requires — systems, team, margin, rhythm. The system becomes visible when the destination is named.

**AI Parse (Destinations):** Solopreneur = 1 person. Small Team = 2-3 people. Valley = 4-7 people (transition zone, not a destination). Team = 8-12 people. Threshold = 13-14 people (Graveyard warning required). Team of Teams = 40+ people (out of scope). The range 15-39 is NOT a destination—it is The Graveyard (Section 3.2.1). Never route advice for 15-39 as if it were a stable destination. Always flag Graveyard territory.

> **Core Principle:** The business will find its center of gravity. The founder's choice is whether to design for it—or change what the business fundamentally is.

**AI Instruction (Destination Design):** When a founder hasn't named their destination, help them name it first. Ask: "Where does the complexity/capacity equation stabilize for your business? What team size does your model, margin, and physics support?" Once named, help them design backward: "What systems, team structure, and rhythm does that destination require?" Do not provide systems advice until the destination is clear — the destination determines the system.

#### 3.2.3 The Defend vs Cross Decision

At your center of gravity, two paths become available. Neither is superior. Both have costs.

> Every decision is binary: the destination behind you or the one ahead.

**The Two Paths**

| Decision | What It Means | What It Requires |
|----------|---------------|------------------|
| **Defend** | Optimize at current destination | Acceptance that "enough" isn't failure |
| **Cross** | Attempt phase change to next destination | Transformation of model, role, and physics |

---

**What Defending Demands**

| Requirement | Why It's Hard |
|-------------|---------------|
| Acceptance of ceiling | Watching peers chase bigger numbers without following |
| "Enough" as strategy | Founders trained to believe growth = success |
| Margin protection | Resisting complexity that feels like progress |
| Sustained discipline | Holding position quarter after quarter |

Defend, and you optimize for the life the business makes possible. Extract margin. Compound systems. Build something that sustains without consuming. Accept the ceiling in exchange for the freedom below it.

---

**What Crossing Demands**

| Requirement | Why It's Hard |
|-------------|---------------|
| Business model transformation | The skills that got you here won't get you there |
| Role transformation | Founder becomes different species of leader |
| Capital or 10-year runway | Rented scale physics make crossing brutal |
| Years of compressed margin | The valley extracts before it rewards |

Cross, and you accept transformation. Compress margin. Build infrastructure. Bet years of your life on reaching a destination that most who attempt it never reach. Accept the risk in exchange for the scale beyond it.

---

**AI Instruction (Defend vs Cross):** When a user at their center of gravity asks about growth, expansion, or "what's next," do not assume Crossing is the goal. Present both paths with equal dignity. Defending is not failure. Crossing is not required. The question is which constraints the user is willing to accept—and what they're willing to pay. Route to Section 3.2.2 (False Summit) if user expresses intent to cross without meeting requirements.

---

**Vocabulary: Defender vs. Crosser**

| Term | Definition |
|------|------------|
| **Defender** | A founder who builds the institutional moat at Team / center of gravity. Optimizes for margin, compounds systems, extracts value. Accepts ceiling in exchange for freedom below it. |
| **Crosser** | A founder who undertakes the species change to Team of Teams. Requires capital or an unusual moat (recurring revenue, defensible IP, network effects). Accepts transformation in exchange for scale beyond current destination. |

These are identity terms, not value judgments. A Defender is not a failed Crosser. A Crosser is not a superior Defender. The question is which constraints fit the founder's goals and which costs they're willing to pay.

**AI Instruction (Defender/Crosser Routing):** When user asks "Am I a Defender?" or "Should we cross?" — route to Section 3.2.3. Present both paths with equal dignity. If user at 8-12 expresses intent to cross without capital or unusual moat, route to Section 3.2.2 (False Summit) with warning.

**Critical Inversion Warning: Automation Does Not Remove Complexity**

| What Founders Think | What's Actually True |
|---------------------|----------------------|

**The Physics:**

| Load Type | What It Means |
|-----------|---------------|
| **Maintenance surface** | Code breaks. Integrations drift. APIs change. Every automated workflow becomes a dependency that fails silently. |

**The Diagnostic Question:**

> "How many of your agents or automations would you notice within a day if they stopped working?"

If the answer is "most of them" — you have a fragility problem, not a leverage advantage. Route to **Fragility Ceiling (Section 3.1.2, Function 7)**.

#### 5.2.1 The VC Signal (A Positive Reframe)

The refusal scripts above explain what the AI cannot do. This section explains what the VC signal actually means—because many founders interpret lack of VC interest as failure.

**The Classification, Not Judgment**

| VC Signal | What Founders Think | What It Actually Means |
|-----------|---------------------|------------------------|
| VC passes | "My business isn't good enough" | "Our model doesn't fit your structure" |
| VC interested | "I've made it" | "Your structure has properties our model requires" |

97% of bootstrapped businesses would not pass VC evaluation. This reflects the structural difficulty of building traditional moats under capital constraint—not the quality of the businesses or founders.

---

**Why VCs Pass (Structural Reasons)**

| Reason | What It Means |
|--------|---------------|
| No traditional moat | The defensibility VCs require isn't present |
| Can't scale with capital | The business model doesn't compound with investment |
| No exit path | Liquidity timeline doesn't match VC fund structure |
| Wrong unit economics | The margins don't support VC return requirements |

None of these are quality judgments. They're structural classifications.

---

**What the Pass Reveals**

| If VCs Pass | Available Path |
|-------------|----------------|
| Traditional moats absent | Institutional moats available (agility, resilience, discipline) |
| VC growth model doesn't apply | Margin optimization available |
| Exit unlikely | "Collect along the way" strategy available |
| Dominance game unavailable | Sustainability game available |

**The pass is information.** It classifies which game is structurally available. A different game—one where institutional moats provide defensibility—becomes the operating path.

---

**AI Instruction (VC Signal):** When a user mentions VC rejection, fundraising failure, or "investors aren't interested," do not treat this as a problem to solve.
